# README and case-study specification

## Public README order

Lead with the concrete promise and an actual current screenshot/clip of the source-backed amount example. Follow immediately with real public sample link, own-file privacy behavior, one-sentence limits and source/build identity. Then present the core loop, supported browser/native capability matrix, three executable local commands, report/replay examples and one parser-upgrade recipe. Deeper sections contain architecture, performance/evaluation receipts, security/contact procedure, license/model/font notices, contribution/task entry point, original repository lineage and measured limitations.

No giant stack badge list or agent-session screenshot as the opening. Do not say install succeeded until the clean-environment command test exists. Do not advertise a hosted API. The local CLI and test corpus are substantial finished features, not a roadmap checkbox.

T49 must execute every command from the README in a clean supported environment, validate all links and tie screenshots to a release tag. The core command examples come from [CLI_AND_REGRESSION.md](../architecture/CLI_AND_REGRESSION.md), not an independent draft syntax.

## Client/recruiter case-study outline

###1. The outcome

Show a real file, two actual readings and the exported explanation. Explain the user problem in ordinary language: an engineer debugging an import needs to locate what went wrong and give someone else reproducible evidence. Do not imply customers already adopted it.

###2. Product judgment

Explain why the original challenge's adjudicator/defaults were the wrong product boundary, why the first screen is a page rather than a dashboard, and why static/local execution avoids anonymous public compute. Show one rejected interface or unnecessary engine with the measured reason, not a menu of abandoned product concepts.

###3. Hard engineering

Walk through one occurrence from original byte hash to page box/UserUnit transform to actual reader output, normalized view/map, alignment, coverage and export. Include the discovered PDFium UserUnit difference and its adapter test. Show the invisible-layer control and an ambiguous alignment where the tool deliberately abstains. State what the API cannot establish.

###4. Reliability and privacy

Demonstrate cancel/replace without stale output, one bad native file among good files, script-free export, malicious import rejection and real canary network capture. Explain what browser workers and containers isolate and what they do not guarantee.

###5. Developer usefulness

Run two isolated reader versions over the same corpus, show a rule-based regression and a coverage-loss failure, verify the baseline did not rewrite itself, and open the report in the browser without upload. Separate “changed” from “regressed.”

###6. Experimental rigor

Present the exact baseline, clean/damaged denominators, held-out family separation, version/model hashes and one negative experiment. State uncertainties, synthetic population and failures. The legacy137.89 challenge result is not this quality measure.

###7. Your work with agents

Use actual task/session/commit records to distinguish owner product/spec/evidence decisions, agent implementation, independent review and manual interventions. A good story is a complex method removed after a clean-control regression—not an invented count of autonomous workers. Do not imply inaccessible provider internals or guaranteed hiring outcomes.

###8. Finished boundary and limitations

Public static app, OSS corpus/contracts and native CLI/regression are complete after their gates. No SaaS accounts, cloud histories, billing, compliance certificate, repair tool or generalized agent platform. Native/browser capabilities and device/language limitations are explicit. End with the actual release/source/test links and measured performance context, not a speculative startup roadmap.

## Evidence slots, not invented achievements

Use `artifacts/gates/G1`–`G5`, exact screenshots, `artifacts/P09`/`P11`–`P15` decisions, `artifacts/performance`, `artifacts/sbom` and immutable source/fixture hashes. Before those exist, write “specified” or “not measured.” A claim slot must not be filled with a plausible number, logo, testimonial or assumed personal contribution.
