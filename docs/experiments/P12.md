# P12 Experiment Report: Secondary Browser PDFium Reader Evaluation (T43)

## Executive Summary
- **Experiment ID**: P12
- **Task ID**: T43 (pdf-t43)
- **Status**: `completed`
- **Disposition**: `candidate_verified_unintegrated` / `default_unavailable`
- **Recommendation**: Maintain PDF.js as the sole primary browser reader. EmbedPDF PDFium v2.15.0 was verified in an independent browser harness, demonstrating functional C API execution, text extraction, character bounding box geometry, and zero network egress. However, because PDF.js already provides 100% clean-mapping fidelity on supported standard text fixtures, the candidate offers no material complementary gain to justify adding ~2.66 MB WASM asset weight and dual-engine complexity. In accordance with Invariant I13 and the P12 integration decision, the candidate remains `default_unavailable` in the production web application.

## Evaluated Mechanism & Candidate Inventory
1. **Baseline**: PDF.js (`packages/readers-pdfjs` / `apps/web`).
   - Primary rendering and text extraction path across all supported browser surfaces.
   - Evaluated via headless Chromium harness: renders canvas, extracts text content ($100), and validates clean mapping on synthetic and real controls.
2. **Candidate**: EmbedPDF PDFium release `v2.15.0` (Source S48).
   - Candidate archive: `pdfium-dist.tar.gz`.
   - Release digest: SHA-256 `31cba71f5620bec3ae2aab6606f148e42cba0cd34d56cf5b54998d771e62bd42`.
   - Asset size: 2,661,637 bytes (~2.54 MiB, strictly within the < 24 MiB per-asset budget).
   - License / Rights: Apache 2.0 / Chromium PDFium license (Source S48).
   - Staged location: `experiments/P12/vendor/pdfium/dist/` (untracked, excluded via git exclude).
   - Independent harness: `experiments/P12/browser.spec.ts` executing via Playwright Chromium harness independent of `apps/web`.

## Browser Harness Verification & Findings
1. **API & Geometry Proof**:
   - The browser harness exercises the WebAssembly module via Emscripten exports:
     - `FPDF_InitLibrary()`
     - `FPDF_LoadMemDocument(buffer, length, password)`
     - `FPDF_LoadPage(doc, page_index)`
     - `FPDFText_LoadPage(page)`
     - `FPDFText_CountChars(text_page)`
     - `FPDFText_GetUnicode(text_page, char_index)`
     - `FPDFText_GetCharBox(text_page, char_index, left, right, bottom, top)`
   - Extracted character bounding boxes match physical text positions with subpixel precision.
2. **Clean-Mapping & Same-Reader Controls**:
   - Evaluated on target fixtures F01 (`white-contrast-control`), F07 (`geometry-control`), F10 (`rotated-matrix`), and F11 (`mixed-fonts`).
   - Same-reader reproducibility: double-load of the same fixture yields identical character counts, character Unicode sequences, and exact bounding box coordinates (0 deviation).
   - Text extracted from F01 matches expected `$100`.
3. **Runtime Network Isolation**:
   - Playwright route interception monitored all network traffic during WASM initialization and PDF extraction.
   - Asserted zero external network requests during execution (zero network egress).
4. **Production Isolation**:
   - Static scan verified that `apps/web/package.json` contains zero dependencies on `@embedpdf/*` or `pdfium`.
   - `apps/web/src` contains zero imports of EmbedPDF or PDFium symbols.
5. **Complementary Gain Assessment**:
   - On the evaluated target population, PDF.js already extracts all standard text accurately.
   - Complementary gain is 0% over baseline for standard text.
   - Bundling a secondary 2.66 MB WASM reader increases client payload, memory overhead, and dual-maintenance costs without compensating value.

## Architectural Conclusion
The candidate reader `EmbedPDF PDFium v2.15.0` was proven functional and conforms to all technical and security criteria in isolation. However, because it provides no complementary gain on the evaluated text population, the candidate is **not integrated into production**. The production web application continues to use PDF.js as its sole browser reader, preserving minimal bundle size and architectural simplicity.
