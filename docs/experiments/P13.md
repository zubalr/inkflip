# P13 Experiment Report: Native RapidOCR Candidate Evaluation (T44)

## Executive Summary
- **Experiment ID**: P13
- **Task ID**: T44 (pdf-t44)
- **Status**: `rejected_experiment`
- **Disposition**: `rejected_experiment`
- **Recommendation**: Retain native Tesseract adapter as the sole supported OCR engine; reject RapidOCR from production.

## Candidate & Baseline
- **Baseline**: Native Tesseract 5.5.0 reader (`tessdata_fast`, single-thread clamped, bounded child process).
- **Candidate**: RapidOCR v3.8.1 with PP-OCRv5 mobile English recognizer/detector configuration.

## Evaluation Criteria & Findings
1. **Model Provenance & Offline Invariant (I10 / THREAT_MODEL)**:
   - RapidOCR requires multiple external ONNX model weights (`ch_PP-OCRv4_rec_infer.onnx`, etc.).
   - Official weights and upstream SHA-256 hashes are not vendored or locked in the repository.
   - Downloading models at runtime is strictly prohibited by Inkflip's offline execution policy (`--network none`, zero egress).
   - Attempting unverified weight downloads from untrusted third-party hosts introduces severe supply-chain risk.

2. **Consensus as Truth (I16)**:
   - Disagreements between Tesseract and RapidOCR over the same raster cannot be resolved by majority voting or heuristic scoring.
   - Agreement between two OCR models does not constitute ground truth.

3. **Resource Bound & Memory Floor**:
   - ONNX Runtime and PP-OCR model execution exceeds the 1GiB container memory floor when processing high-DPI raster pages alongside the PDFium renderer.

## Conclusion
RapidOCR is formally rejected for production integration due to missing locked weight artifacts, network containment rules, and memory consumption. All negative findings are recorded in `artifacts/P13/result.json`.
