# Inkflip: independent workbench roadmap

September 13, 2026. This is a static ownership/implementation plan, not a second task tracker. Beads remains live authority. The packet reflects the owner's latest preference: use Devin CLI for difficult work, Antigravity for interface work and ZCode for volume, without agent-to-agent chat.

**Readiness:** task allocation and starter packets are prepared and checked. The operational change below is not installed and these are not active grants. Do not launch competing writers from these files. The existing integrator adopts the plan once at a safe checkpoint; no additional product decision is needed for the described ordinary work.

## Outcome and constraints

Finish the existing browser inspector and native/corpus/regression product. Reduce idle time by assigning stable queues to independent workbenches, preserving real dependencies, scope ownership, independent review and final merged gates. No chat messages, provider handoffs, duplicate Goals or repeated user routing between tasks. Git checkpoints, published Beads grants and review files are the asynchronous interface.

Literal zero shared state would not work for one application. This design removes conversational coordination: sessions read an agreed contract and a shared board, produce commits, and continue eligible work. One integrator still accepts and publishes merged work. A published branch is not an accepted feature.

## Autonomous execution without chat

Each session reads its published grants and committed review files, selects its first eligible item, implements/tests in its own checkout, and publishes a checkpoint with the repository's existing receipt/handoff. It then chooses another eligible independent task or reviews a candidate. When every item is blocked, it records one concrete blocker in its own artifact and uses the existing bounded native resume/poll behavior; it does not spawn a supervisor or repeatedly message the owner.

A checks every lane's new refs and E's review artifacts on every coordination cycle (30–60 seconds while actively waiting). A makes reviewed integrations available promptly, writes acceptance/next grants and publishes state. This is mechanical file/state exchange, not a chat handshake. Dependency consumers wait for the published accepted change; no user must relay messages.

E's highest priority is reviewing other lanes. Every task E implements requires another qualified, nonauthor reviewer from a yielded lane, in a separate review checkout. A may own final acceptance but never substitutes its self-review for independent review. T55 specifically uses a fresh nonauthor Devin reviewer in the E slot: E's earlier authoring session commits its evidence and yields, and A assigns the full merged-candidate T55 contract to that fresh session. An extra review of one E-authored task is not a substitute for the full independent final review. This replaces the E session within the five-slot budget. Gate scenario authorship, independent review and acceptance remain distinct.

All packet outputs use existing per-task artifacts and refs. Do not add another markdown/JSON completion ledger. `roadmap.json` contains static routing/contracts only; `validation.txt` is evidence of this plan check, not ongoing progress.

## Completion and limitations

Success is measured by the shipped public journey, the real native CLI/corpus upgrade workflow, passed capability/quality gates, honest documentation and authorized release steps. Session count and generated lines are not completion metrics. Required manual/device evidence remains explicit; do not fabricate it to keep the queue moving.

If the new admission mode fails validation, keep its mode disabled and preserve existing work/grants. The old dispatch path remains available while the defect is fixed. Do not revert candidate work or reset checkouts to roll back scheduling.

This packet creates no sessions and changes no live claims. It is ready for the integrator's one-time implementation/adoption, not yet a deployed scheduler. Source snapshot and static coverage checks are in validation.txt. Start with A-START.md, then the appropriate B/C/D/E packet after activation.
